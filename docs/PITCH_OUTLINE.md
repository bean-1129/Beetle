# Beetle pitch outline (six slides, five minutes)

Reframed 2026-10-03 14:22 CDT around the generator: any game request becomes a playable game inside a bounded, growing library of engine mechanics, and the designer keeps changing it while people play. Updated 15:15 CDT for streaming generation (the world starts where the players are and grows as they move) and 15:28 CDT with its measurements (docs/ACCEPTANCE.md streaming section, three runs on a contended GPU; docs/RESULTS.md 15:16 CDT, one run on a quiet GPU). Every number below is copied from the file named next to it; nothing is estimated. Where a measurement does not exist the line says so instead of carrying a number. GPU state is labelled on every timing because the Ollama daemon was shared with other owners' runs for most of the day (docs/MODEL_SELECTION.md section 2).

## 1. The problem and the user

- Technical designers at small studios iterate on playable prototypes by stopping the session, editing, rebuilding, and re-gathering playtesters.
- Every "stop" costs the thing they are trying to observe: how people actually play.
- Beetle's promise: change the game without stopping the game.

## 2. Any game, one prompt, then keep changing it while they play

- One prompt in, a playable 3D game out: the agent maps any game request onto the closest supported mode and biome, says which it chose, and composes a world that two people join from their phones.
- The mode library (packages/contracts/src/limits.ts, `GAME_MODES`): relic_hunt (collect relics, enter the gate; `relicsRequired` 1 to 3), time_trial (the same against `timeLimitSec` 20 to 600 s, default 120), king_of_the_hill (hold the zone for `holdSeconds` 3 to 60, default 10), checkpoint_race (relics as ordered checkpoints, then the gate), survival (the hazard plane rises after `afterSec` at `metersPerSec` up to `maxElevation`, every bridge submerges once it passes -1.0 m; grab a relic and reach the gate before the timer). Five biomes: garden, volcanic, frost, desert, night. Two hazards: water, lava. Movement speed 3 to 7 m/s. Eleven decoration types.
- Starts where the players are, grows as they move, every extension validated before it lands. With streaming on (`streaming` in the world spec; the server switch `autoExpand` defaults to on), the brief builds only the zone around the spawn (the streaming brief rule asks for 2 to 4 islands, `STREAMING_BRIEF_RULE` in packages/agent/src/expansion-prompts.ts). When a player nears an edge with no crossing beyond, Beetle extends the world ahead of them: each extension is a small patch of 1 to 2 islands that goes through the same validator and commit path as any edit. Growth stops at 24 islands and 48 bridges (`WORLD_LIMITS`, `STREAMING.maxIslands`), and the director can switch it off from the director page. Measured (slide 5): extension request to commit 10.6 to 65.9 s on a contended GPU, 4 of 6 committed (docs/ACCEPTANCE.md), 9.5 s once on a quiet GPU (docs/RESULTS.md); the trigger opens the request within 0.3 s. The spawn-zone brief time is not measured; do not quote one.
- Then keep changing it while they play: `set_mode`, `set_biome`, `set_movement` join the structural patch ops; every change is validated by game code and committed without a reset (docs/ARCHITECTURE.md "Mode library and generator mapping").
- What Beetle takes from one-prompt game generators and what it adds (docs/COMPETITIVE.md): the one-prompt front door and instant playable output are adapted; live editing without a reset, deterministic validation and repair before publish, local-only inference and phones as controllers are added. No vendor fact is claimed that cannot be verified offline.
- One machine, one local model, one real agent runtime (OpenClaw), zero cloud. OpenClaw is verified end to end against the real server: an edit committed v2 in 20.0 s with real tool calls (13:43 CDT), the gated test committed in 38.9 s with 7 tool calls, a fresh brief committed v1 in 33.4 s (docs/RESULTS.md, BUILD_STATUS.md case 17). Direct-mode numbers are labelled `[direct]` in every report.
- Status of the mode library at 14:50 CDT (BUILD_STATUS.md 14:36 CDT): contract, validator (`MODE_INVALID`), patch ops, movement speed, session summary, the server rule per mode, the mapping prompt and the biome presets are implemented; 29 mode unit tests, 50 in-process server tests and the five-mode integration test on a real server with real controllers (5 of 5) pass; the frost hill fixture is verified in the browser. Mode briefs measured at 14:25 to 14:42 CDT (slide 5).

## 4. Agent architecture and validation

- WorldSpec (structure, including `mode`, `biome`, `movement`, `hazard.rise`) is separate from SessionState (players, relics, score, and the mode-dependent `objective` the simulation advances). Versions advance only on committed transactions.
- The mapping step: the brief prompt lists the five modes, five biomes, two hazards and the speed range; the model picks the closest mode and biome for any request, fills the parameters from the brief ("hold ten seconds" becomes `holdSeconds: 10`), and states the mapping. Structured output under `WORLD_DRAFT_JSON_SCHEMA` means only a listed mode kind, a listed biome and in-range parameters can be emitted; a game the library cannot express lands on the nearest kind and the agent says so rather than inventing rules.
- Two ways a request starts: the director types one, or the frontier trigger opens one (apps/server/src/expansion.ts). The trigger fires when an active player stands on an island within `STREAMING.frontierMeters` (4 m) of its rim and no bridge endpoint on that island lies within 45 degrees of that direction; the server checks players about once a second, keeps one automatic request in flight, and waits at least `STREAMING.cooldownMs` (12 s) between extensions. The request is marked `auto` with `autoReason` (island, direction, player), and the director's activity trail labels it.
- The extension op is `add_island` (packages/contracts/src/patch.ts): a new island with centre and radius 4 to 14 m, bridged from an anchor island (`bridgeFrom`, or the nearest island). Patch application pushes the island clear of existing islands (1.25 m gap) and inside the bounds, refuses it with `RESOURCE_LIMIT` at 24 islands, and adds the bridge only while under 48 bridges; the result then goes through the full validator like any patch. `remove_island` also exists and refuses an island that carries a spawn, relic or the gate.
- The agent reads state, proposes, validates, repairs within a bounded budget (at most 2 repair attempts, `BEETLE_MAX_REPAIR_ATTEMPTS=2` in .env.example; the `attempts` field in every failed run report reads 3, one first try plus two repairs), commits only with a server-issued proof, and reports.
- Validation is deterministic game code: geometry, bridge sockets, duplicate bridges, walk field, reachability with the gate locked, occupied-support checks at commit time, and now `MODE_INVALID` cross-field rules (relics required above the relic count, checkpoint_race with fewer than 2 relics, survival without a rising hazard or with a `maxElevation` that never rises, a time limit outside 20 to 600 s). The mode rule itself is engine code selected by an enum. An LLM saying valid is never approval.
- Nothing from the model is executed. Output is schema-checked JSON only. Since 13:05 CDT a deterministic normalizer (packages/world/src/normalize.ts, docs/ARCHITECTURE.md "Model-output normalization") maps display names and compass words to real ids and pulls offsets back inside the island before the strict schema and the full validator run; it never bypasses reachability, gate or occupancy checks.

## 6. Business hypothesis and next validation

- Hypothesis: studios will pay for faster prototype iteration that keeps playtests running, with data staying on their machines.
- Not claimed: market size, pricing, customer traction, speed-up percentages without a measured baseline, and nothing about any named one-prompt generator that was not verified offline (docs/COMPETITIVE.md).
- Next validation: time a conventional edit-rebuild-regather loop with the same designers and the same change list, and compare against Beetle's measured edit-to-commit times (2.0 / 8.0 / 14.0 s in run 3; 8.0 s with two players moving in the acceptance run).
