## Verified good

The Beetle client asserts a loopback server URL (`tools.ts:99`); the OpenClaw plugin reuses it (`openclaw-plugin/src/index.ts:8, 94-99`). `loadConfig` throws on any non-loopback `OLLAMA_BASE_URL` or `BEETLE_SERVER_URL` (`config.ts:79-80`). Covered by `tests/unit/agent.test.ts:231-266` (case 15): a refused model yields `MODEL_UNREACHABLE` and every request seen by the spied `fetch` went to one of the two loopback hosts.
- The OpenClaw profile (`.openclaw-home/openclaw.json`, generated by `openclaw.ts:64-110`, read 12:52): `models.mode: replace` with exactly one provider (`ollama`, `baseUrl http://127.0.0.1:11434`, api `ollama`) and one model (`qwen3.5:4b`, `reasoning: false`, `think: false`); `agents.defaults.model.primary ollama/qwen3.5:4b`, `fallbacks: []`; `thinkingDefault: off`; `tools.profile: minimal`, `alsoAllow` = the plugin and its seven tools only, `deny` lists 80 core tools including exec, terminal, process, read, write, edit, browser, fetch, web_fetch, web_search, sessions_*, plugins, secrets; `toolSearch: false`; `exec.security: deny`; `fs.workspaceOnly: true`; `web.search.enabled: false`, `web.fetch.enabled: false`; `gateway.mode: local`, `bind: loopback`, port 18799, token auth; `plugins.allow: [beetle-tools]`. The config file is mode 0600 and the home directory 0700; `.openclaw-home/` is gitignored. Auth

- Director routes (invite, requests, request by id, activity, reports, undo) all call `requireDirector` first (`http.ts:167-223`). - Controller tokens live only in `SessionStore.controllerTokens` and are consulted only by the WebSocket controller hello (`ws.ts:137-160`); `requireDirector`/`requireAgent` compare against the director/agent secrets, so a controller token gets 403 on both route families by construction. Limits and validation
- HTTP body limit 1 MiB (`index.ts:217`); JSON parser replaced so an empty body is `{}` and invalid JSON is a 400 (`http.ts:35-50`).
- WebSocket `maxPayload` 16 KiB at the library and a 4096-byte close (1009) in the handler (`ws.ts:45, 218-222`); binary frames rejected; `perMessageDeflate` is off by default in ws 8.
- Input rate limit 60/s per player with a sliding one-second window (`ws.ts:200-209`), tested in `protocol.test.ts:142-151`; stale or out-of-order `seq` ignored (`ws.ts:210`); axes clamped (`ws.ts:213, 401-403`).

Same severity scale as above.

**Executable-code rule ("runtime model output must never become executable JavaScript"): DOES NOT COMPLY.** For any idea matching `SCRIPT_IDEAS` (`gen/script.ts:15`), the local model writes plain JavaScript (`gen/script.ts:32-55`, field `code` in `SCRIPT_SCHEMA`), it is stored verbatim in `spec.script.code` (`gen/script.ts:77`), wrapped by `scriptWrapper` (`runtime/script.ts:253-255`) and emitted as an inline `<script>` in the staged play page and in the exported file (`export/export.ts:44`). The same happens for "change in words" on a scripted game (`gen/ai.ts:169-179`, the model rewrites the whole code) and for code typed into the Code panel (`ui/Studio2D.tsx:1286-1310`). Containment today is (a) a regex denylist `checkScript` (`runtime/script.ts:216-231`), which is not a boundary, (b) an iframe with `sandbox="allow-scripts"` and no `allow-same-origin` (`ui/Studio2D.tsx:279`, `:836`), and (c) a meta CSP `default-src 'none'; script-src 'unsafe-inline'` in the page (`export/export.ts:6`, `:32`). `new Function` exists only in `compileScript` (`runtime/script.ts:296-298`, Node and tests). There is no custom interpreter; the model's code runs as real JavaScript. The hand-written samples (`samples/scripts.ts`) are static developer code; `fillTemplate` (`samples/scripts.ts:503-507`) only splices words reduced to `[a-z -]`, so the template route does not carry model code.

What would make it comply (smallest first): (1) disable the model-written route: in `gen/ai.ts` stop calling `writeScriptGame` and `changeScriptInWords` (route `SCRIPT_IDEAS` to the closest built-in genre or to a hand-written `SCRIPT_TEMPLATES` entry with `fillTemplate`), and make `repairSpec`/`validateSpec` drop `spec.script` unless `code` equals one of the shipped template texts after `fillTemplate`; or (2) keep scripted games but have the model emit a declarative JSON DSL (objects, tags, rules such as "on key left set vx -8", "on hit tag coin add score 1") that `ScriptGame` interprets, with no string ever reaching a `<script>`. Option (1) is a one-file change for the demo; option (2) is the long-term design.
